# 有限日期窗口显示边界修复

多事实窗口查询和解释现在接受合法的有限 INT32_MIN 日期
`5877642-06-23 (BC)`，保留既有完整有限 DATE 支持范围。固定 DuckDB 能格式化
这个日期，却不能把该文本转换回 DATE。[原失败](../p1-finite-date-window-defect/probe.json)
不是业务拒绝；修复请求解析后，仍因窗口编译器把日期转文本再解析而执行失败。
现在历史与多事实共用有限日期解析，窗口显示边界保留为 typed DATE 常量的查询树。
窗口仍先计算全捕获，再按日期显示；没有变成日历补齐或前置过滤。

[实际结果/计划/decoder 对照](verification.json)与[新产物 receipt](receipt.json)
绑定 macOS ARM64 `e04ff401f37318a92d381f5454ff47c6683d8c52288db8d7d3348eb5b2cf9e71`。
五个有限日期包含孤立下界、下界后的合法日、BC 宽年份、epoch 和最大有限日，
均核对完整窗口行与独立整数金额计算；十项无限/哨兵/越界请求在 query/compile
均拒绝。原生 95 项 fact program 控制证明 typed 树绑定/执行/完整行/耗尽成功，
而渲染文本仍不可独立执行。264 项生产捕获检查含空显示范围的最小日期接受。

实际 fact MCP 37 检查/48 拒绝通过，新增 finite-minimum 场景核对完整成员与金额，
旧 wide 样本保留五个日期。曾直接给旧样本增加一行，导致历史验收对应改变；
现通过独立新场景补边界，旧原始报告没有覆盖或改写。其余五原生 runner、
30 SQL/1,079 断言、138 Bun/723 expects、类型/格式/架构通过。
同一新产物的 P0、全部旧 SQL/五 MCP/五无模型封存重放，以及历史 load/links/
plan/MCP 全部复验通过，历史 MCP 为 15 检查/24 拒绝/28 损坏控制。
