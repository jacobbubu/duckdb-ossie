# Linux 重放失败的确定性边界调查

调查确认一个可复现的生产/重放边界缺口：受控回调发生时，生产端可能在
记录耗时尚未达到限额前取消工作；重放器拒绝这种记录，报出与 Linux CI
相同的缺响应断言。原 CI 的私有失败轨迹不可得，仍不能认定它就是本次
CI 的实际根因。本轮完成复现和候选评估，没有修改正式实现或重跑 CI。

沿 OSSIE-REQ-001、`5ffc96a`，仅使用本地已有、与当前 68 来源文件一致的
成功无模型档案。原档案不可变；新样例均另存、重新封存并标为合成衍生，
不是原 Linux 运行轨迹，也不是真实 Agent 验收。

## 边界与拒绝保护

以同一个限额 250 毫秒的超时档案为来源，保持事件顺序、失败类别/原因、
摘要和失败文件一致，只改变末尾失败事件的记录耗时：

| 记录耗时 | 当前重放结果 |
| --- | --- |
| 249 ms | 拒绝，`ordered event expected: simulation_response` |
| 250 ms | 返回 `failed`，诊断重放一致 |
| 251 ms | 返回 `failed`，诊断重放一致 |

七项负控全部拒绝：缺响应而下一条是 provider_response、缺响应到 EOF、
非超时终止、failure 文件不符、summary 不符、终止后多余事件，以及用
伪造超时事件替换成功响应而保留后续轨迹。它们没有被允许冒充成功执行。
这不声称能鉴别所有协调重封的伪造：seal 的合同仍是相对字节完整性，
不是提供方真实性或外部时间证明。

十个重放样例全部阻断 fetch 和子进程，观察到的调用数均为零。原 timeout
及 positive 两个 seal 在实验后完全保持。

## 生产端的受控验证

用手动受控的 `Date.now` 与计时器回调分别测试 `beforeDeadline` 和
`agentLoop`：限额为 10 ms，在记录时钟走到 9 ms 时触发已排定的回调。
当前两条路径均取消工作，报 `scenario deadline exceeded`。这是代码在
该调度条件下的确定行为，不是对真实 Bun/Linux 计时器调度的观测。

官方规范将 Date.now 定义为调用时的 UTC 时间值；Node 文档不保证 timer
回调的精确触发时刻。它们不能证明此 CI 的 Bun 1.3.11 提前触发，也不能
替代缺失的 Linux 原轨迹。[ECMAScript Date.now](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-date.now)、
[Node timers](https://nodejs.org/api/timers.html#settimeoutcallback-delay-args)。
当前 [Bun 日期测试文档](https://bun.com/docs/test/dates-times)可作测试机制
参考；本轮实际采用已安装版本的 spyOn 手动控制，不以新版文档推断旧版
运行行为。

## 可审阅候选及发现的限制

[候选 diff](candidate.patch.txt)仅针对共享 agent_loop 模块：回调取消前
重新检查同一个绝对截止时间，未到则只等待剩余时间；清理函数取消最新
timer 并阻止陈旧回调复活。配置预算、错误身份、重放规则和归档格式均
保持。完整候选保留在忽略的本地目录，正式源码未应用。

外层 deadline 与内部 loop 各做 pending、success、multiple-early 三种
受控检查，共六项通过；已过期请求不启动。成功后和超时后没有剩余
timer，陈旧回调不能继续排期。候选在稳定记录时钟下消除了已演示的
提前取消缺口。

额外三项检查确认了重要限制：action 原拒绝保持、timer 正确释放；时钟
向前移动会按截止判断；时钟回拨会追加剩余等待。在一个 10 ms 的例子中，
回拨后的剩余排期变为 11 ms。因此“配置值不变”不能说成“实际等待边界
完全不变”。截止检查与事件记录之间若再次回拨，记录仍可能落回阈值前。
该候选不是完整的单调时钟方案，也不能声称已经修复原 CI。

只读 Advisor 支持稳定时钟下的窄修复，同时指出上述共享消费者与回拨
风险；Lead 额外复现了回拨行为，保留候选而未直接集成。请求为
Advisor/Astra/high，有效身份、用量和计费未知。
