# 每天合格User集合：研究契约与最小验收

2026-10-11，OSSIE-REQ-001现多期工作项。用户只授权研究，基线bd8c0ee。
本文件提出可评审候选，不修改生产profile、ontology/mapping、MCP、Agent
提示词或已有验收裁定。原八行和真实实验原件保留；新fixture全部为合成数据。

## 结论与范围

建议第一候选明确命名为**冻结观察数据中，每个指定自然日均有合格见证的
用户集合**。在所选产品范围内，每一天至少一条观察满足当前正式规则，
就满足该日；每天可以来自不同产品，同日其他不合格观察不抵消合格见证。
这不是每个产品每天都合格、同一产品连续合格、所有观察都合格或期末合格。
未入集合只表示缺少所需见证，不推断用户真实状态或采集遗漏原因。

固定[ontology规范](https://github.com/apache/ossie/blob/8dd6732da354f22ca71f16d82626a46039ecdcd9/ontology/ontology.md)
给出实体标识、集合关系和派生概念构件；这些构件不替本项目决定此查询的
日期/产品参数、业务日历、数据完整性与缺失政策。
[表达式提案](https://github.com/apache/ossie/blob/8dd6732da354f22ca71f16d82626a46039ecdcd9/core-spec/expression_language.md)
限制表达式内SELECT、子查询、GROUP BY及集合查询；下面的普通SQL只作
独立oracle，不是OSSIE_SQL_2026表达式、可加载模型或执行器支持证明。
来源采用仓库固定8dd6732副本，在线核对同一commit，未改用main最新规范。

## 候选决策表

| 事项 | 第一候选 | 仍需区分的业务意义 |
| --- | --- | --- |
| 日期 | 操作者明确首尾含的有限DATE，start≤end；D为其间全部自然日且非空 | 不从已有行推断日期，不自动去掉周末/假期；工作日历是另一范围 |
| 观察日 | 已提供的DATE原值 | 不接受TIMESTAMP自动截日，不推断时区 |
| 缺失日 | 无合格见证则不入集合；不补零、不沿用前日、不删该日 | 不能因此判定真实用户不合格；若要求真实全期资格，需要额外完整性证据/政策 |
| 分类NULL | 正式规则只有TRUE提供见证，FALSE/UNKNOWN均不提供 | NULL不是0，也不是明确低于阈值 |
| 金额NULL | 不影响本集合 | 本包只有用户成员/人数，无金额或比率分母 |
| 产品 | 明确all或非空集合P，成员为非NULL、非空原始String；存在式选取范围内任何产品 | 产品可跨日更换；all不表示每个产品都必须满足 |
| 未匹配产品 | 候选沿现String过滤语义：明确P={Z}合法，但无匹配则空集合 | Z未出现不是“非法产品”的证明；拒绝需产品catalogue权威，不自动回退all |
| 空产品列表 | 显式subset但P=∅候选拒绝；与all分开 | 全批无记录时all请求合法且结果为空，不把它当非法显式空列表 |
| 身份 | 保留既有raw user_id及typed(user,date,product)身份 | 不trim/casefold，不按产品另造User；不把观察ID当人数 |
| 重复 | 全批typed tuple预检，完全重复/值冲突都拒绝，包括范围外 | 查询不能先过滤来隐藏重复，不latest-wins |
| 规则与快照 | 同一冻结批次与同一当前正式规则应用于所有请求日期 | 不是每个日期历史有效规则、as-of或修订回放 |

以上缺失/日历/all/subset为项目候选约定，尚未获业务或实施批准。若用户
提问未明确自然日、产品范围或是否需要真实业务完整性，不能默默套默认。
裸“每天都合格”仍有歧义；实际API/指标名字、规则表达、版本与载入方式
在后续实现设计中决定，本研究不新增这些接口。

## 精确集合与量词

U为冻结批次的raw User集合；D为请求的非空日期集合；产品范围用all或P
显式区分。对每个d定义S(d)={u∈U：存在一条(u,d,p)观察，p在所选范围，
且正式资格规则为TRUE}。候选Q为所有S(d)的交集，人数为|Q|，空结果为0。
日期数|D|是覆盖条件，不是金额分母；本包不提供比例及比例分母。

| 量词 | 含义 | 本23行fixture的两日成员 |
| --- | --- | --- |
| ∀日 ∃产品 | 每日在范围内至少有一条合格观察，可换产品；候选 | B,E,F,H,K（5） |
| ∃产品 ∀日 | 至少一个固定产品每天合格 | B,F,H,K（4） |
| ∀日 ∀产品 | 范围中每个产品每一天都有合格观察 | K（1） |
| 每日有合格见证且范围内所有观察均TRUE | 另一个更严格条件，NULL也不能通过 | B,E,H,K（4） |

后两种人数为4的成员不同，证明仅比人数不足以验收。所有产品对照域固定
为整个批次的{X,Y}，不能逐日缩小∀产品要求。对候选的∃产品而言，all
与使用冻结批次所有已观察产品集合等价；不会凭空产生未观察产品见证。
这里的∩符号与普通SQL双NOT EXISTS仅描述数学/独立见证，不承诺表达式
提案允许INTERSECT或子查询。空D拒绝，以免真空成立选中全部U。

## 后续最小验收边界

若候选获接受，下一设计包先确定规则/请求/发现的承载方式及选择条件如何
注册；不能给现User referent-only直接放开查询，或让Agent客户端重算
能力外结果来通过旧第四场景。暂不设计通用窗口/工作日历、每产品∀条件、
金额/比例、as-of、多事件/修订或多事实；也不更改现user_count的存在式含义。
未来成功证据须同时给日期集合、产品模式/子集、规则及冻结绑定、真实
执行成员来源与整数人数；不能只给五这个数字或一个compile诊断plan。
日期跨度、输入/响应预算、取消与资源门禁也须在实现设计中明确；本研究
只验证小范围，不承诺任意长日期区间或无限制User×日期枚举。
